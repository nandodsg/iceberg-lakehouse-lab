# Iceberg Lakehouse Lab

**Status:** Living design document --- v0.2\
**Role:** Source of truth for the Iceberg Lakehouse Lab

## 1. Purpose

Build a public, portfolio-grade Data Engineering laboratory that
compares **Databricks** and **Snowflake + dbt + Airflow** over a shared
**Apache Iceberg** data foundation.

The Lab is designed to maximize:

-   practical Data Engineering learning;
-   job-market-relevant skills;
-   reproducible implementation;
-   evidence-based architectural decisions;
-   cost discipline;
-   portfolio-quality documentation.

The Lab is **not** initially the production analytics platform of Matriz
de Senioridade. Any future production adoption is a separate decision.

## 2. Core principle

The architecture is a deliberate **learning baseline**, not a blank
slate.

When a business question appears:

1.  First test whether the existing architecture can answer it.
2.  Prefer reformulating the question rather than redesigning the
    architecture.
3.  Allow targeted architectural changes when there is a strong
    justification.
4.  Do not systematically redesign the Lab around every new question.

The project follows:

> **Problem → Hypothesis → Experiment → Evidence → Learning → Decision**

## 3. Initial Data Product

### Business journey

The first analytical journey is **Gestão de Entidades**.

A successful journey is defined as:

> A company has at least one team with at least one member.

The intended product flow is:

``` text
Create Company
      ↓
Create Team
      ↓
Create Member
```

The application currently redirects the user automatically to the next
logical step.

### Initial analytical question

> **How does the user's navigation behavior through the Gestão de
> Entidades journey relate to successful completion of the journey?**

The Lab will use this journey because it is simple enough to keep the
initial pipeline focused while exercising the intended architecture.

## 4. Behavioral experiment

The Lab incorporates an **Agent-Based / E2E behavioral data generator**.

The agents operate against the **real Matriz application in DEV/STG**,
not against a copy or simulated UI.

DEV/STG are isolated environments containing synthetic accounts and
data.

The initial experiment compares:

-   **Guided:** completing one step automatically redirects the agent to
    the next step.
-   **Unguided:** completing one step does not automatically redirect
    the agent.

The initial hypothesis is:

> **Agents exposed to the Guided flow have a higher probability of
> completing Company → Team → Member within 10 minutes than agents
> exposed to the Unguided flow.**

The ABM is deliberately subordinate to the Lakehouse Lab. It should only
gain complexity when that complexity materially improves the
data-generation needs of the Lab.

## 5. ABM as a data generator

The ABM/E2E component is not initially treated as an independent
product.

Its role is to generate controlled behavioral data by executing journeys
in the real application.

Conceptually:

``` text
Agent parameters
       ↓
Claude Code / E2E automation
       ↓
Matriz DEV/STG
       ↓
 ┌─────┴─────┐
 ↓           ↓
GA4       Supabase
 ↓           ↓
BigQuery    PostgreSQL
 └─────┬─────┘
       ↓
   Lakehouse Lab
```

The ABM may eventually become an independent portfolio repository if it
demonstrates sufficient standalone value. That is a graduation decision,
not a current architectural requirement.

Detailed ABM behavior, parameters, execution rules and scope are defined
in `abm/abm_data_generator.md`.

## 6. Data sources and boundaries

The initial sources are:

### Matriz / Supabase

Provides application state and entities such as:

-   companies;
-   teams;
-   members;
-   relevant lifecycle/state information.

### GA4 / BigQuery

Provides behavioral events generated by interaction with the
application.

**BigQuery is a source system for the Lab, not a third comparison
engine.**

The extraction mechanism may evolve in the future, but the analytical
contract should remain independent of whether data arrives through
BigQuery, an API, MCP, or another approved mechanism.

## 7. Privacy and trust boundary

The Lab repository is public. Every committed artifact must therefore be
safe to assume permanently public.

Never commit:

-   production data;
-   production credentials or connection strings;
-   raw STG exports;
-   identifiable user data;
-   authentication tokens or API keys;
-   the full private Matriz schema or migration history.

Matriz DEV/STG may contain synthetic data and may be used by the ABM.
Nevertheless, data leaving the Matriz repository/system must pass
through an approved **privacy-safe export contract**.

The Matriz repository owns the contracts defining what it is permitted
to export.

The Lab consumes those contracts. It does **not** maintain copies of the
Matriz export contracts.

Data contracts should use the **latest available Open Data Contract
Standard (ODCS)**.

## 8. Contract boundaries

The separation of responsibilities is:

``` text
Matriz
  │
  │ defines what may be exported
  ↓
Safe Export Contract
  │
  ↓
Iceberg Lab
  │
  ├── ingestion
  ├── transformation
  ├── quality
  └── analytics
```

The Matriz repository should know only what is necessary to provide its
approved data contract. It does not need to know the internal
Databricks/Snowflake architecture.

The Lab owns the contract for data generated by the ABM.

## 9. Target architecture

``` text
Matriz DEV/STG ──┐
                 │ approved privacy-safe exports
GA4 / BigQuery ──┘
                 ↓
             AWS S3
                 ↓
       Apache Iceberg + Glue
                 ↓
        ┌────────┴────────┐
        ↓                 ↓
   Databricks         Snowflake
   Spark / SQL       SQL + dbt
        │                 │
        └────────┬────────┘
                 ↓
       Equivalent Gold Outputs
                 ↓
       Comparison / Analytics
```

The first implementation is batch-oriented and intentionally minimal.

  Orchestration             Apache Airflow

## 11. Repository structure

``` text
iceberg-lakehouse-lab/
├── foundation/              # pre-fork, shared by both tracks
│   ├── infra/               # S3, Glue, IAM
│   └── ingestion/           # Matriz/GA4 → Iceberg bronze
├── tracks/                  # post-fork, one independent subtree per engine
│   ├── databricks/
│   │   ├── infra/
│   │   ├── transform/       # Spark/SQL bronze→silver→gold
│   │   └── quality/
│   └── snowflake/
│       ├── infra/
│       ├── dbt/
│       ├── airflow/
│       └── quality/         # dbt tests
├── contracts/               # cross-cutting — outside foundation/ and tracks/
├── docs/
├── abm/
│   ├── abm_data_generator.md
│   └── experiments/
├── .github/workflows/
├── LAB.md
└── AGENTS.md
```

The split is by **when something runs in the pipeline**, not by tool:
`foundation/` is produced once and read by both tracks; `tracks/<engine>/`
is where each engine's own implementation lives, and the two never share
code. Each `tracks/<engine>/infra/` is an independent OpenTofu root module
with its own state. State separation, not just folder separation, protects
the blast radius: a Databricks apply must not manage Snowflake resources,
and neither must manage `foundation/infra/` except through explicitly
shared outputs. This is what makes graduation possible without
entanglement: the losing track can be dropped, or the winning one kept,
without touching the other. `dbt/` and `airflow/` live only under
`tracks/snowflake/` because that track's design explicitly names them
(§10); Databricks orchestrates and transforms with its own Jobs/Workflows
and Spark/SQL instead, so nothing shared would ever use them.

`contracts/` stays outside both `foundation/` and `tracks/` on purpose: it
is not pipeline-stage-shaped like everything else here — it is an interface
layer spanning the ingestion input contract *and* both tracks' Gold output
contracts.

The ABM (`abm/`) follows the same graduation logic as its own, separate
concern: everything needed to run it — design doc, experiment configs,
decision harness — lives inside `abm/`, so the whole module can be
extracted into an independent repository later (§16) without untangling it
from the rest of the Lab. Its output contract is the one deliberate
exception: it stays in top-level `contracts/`, owned by the Lab (§20 of
`abm/abm_data_generator.md`), so the interface the Lab depends on survives
unchanged even if the producer behind it moves.

The Matriz export contracts remain authoritative in the Matriz
repository.

## 12. Learning route

The Lab intentionally progresses through:

1.  governance and cost guardrails;
2.  shared AWS/Iceberg foundation;
3.  safe batch ingestion;
4.  Databricks track;
5.  Snowflake + dbt + Airflow track;
6.  interoperability proof;
7.  CI/CD and portfolio evidence.

In practice step 3 was built and proven before step 2 existed: the
batch extractor runs against a local Iceberg catalog first (zero cloud
spend while the pipeline is unproven) and moves to the shared AWS
foundation by configuration, not by code change. The order above still
describes the target platform; local-first is how each step earns its
cloud cost.

The ABM/data generator is introduced as the source of realistic
synthetic behavioral data without becoming a parallel engineering
project.

The Lab should produce hands-on evidence of:

-   S3 and cloud foundations;
-   Apache Iceberg;
-   AWS Glue Catalog;
-   Spark / Databricks;
-   Snowflake;
-   dbt;
-   Airflow;
-   OpenTofu;
-   data contracts;
-   data quality;
-   lineage and governance;
-   CI/CD;
-   observability;
-   reproducibility;
-   cost management;
-   interoperability.

## 14. Quality and observability

The ingestion layer should record, where applicable:

-   row counts;
-   schema validation;
-   load timestamp;
-   source watermark;
-   rejected records;
-   contract validation results.

The dbt layer should include meaningful tests such as:

-   `not_null`;
-   `unique`;
-   `relationships`;
-   `accepted_values`;
-   custom business rules.

## 15. Comparison principle

Databricks and Snowflake must process the **same approved dataset** and
produce equivalent analytical outputs.

Comparison must be based on evidence across:

1.  learning value;
2.  job-market relevance;
3.  actual cost;
4.  time to reproducibility;
5.  IaC and CI/CD;
6.  quality and recovery;
7.  governance and lineage;
8.  Iceberg interoperability;
9.  batch and future streaming viability;
10. operational complexity and maintainability.

The Lab must distinguish:

> **best platform for learning**

from:

> **best platform for operating Matriz de Senioridade at its actual
> scale.**

## 16. Graduation criteria

The comparison is complete when:

-   both tracks process the same approved privacy-safe dataset;
-   both produce equivalent validated Gold outputs;
-   setup and teardown are reproducible;
-   costs and limitations are documented;
-   interoperability claims are demonstrated with evidence;
-   a winner is selected using the rubric;
-   the distinction between learning platform and production platform is
    documented.

At graduation, the winning architecture may continue in this repository.
A separate production repository should be created only if that
separation has a clear benefit.

The ABM may also graduate into its own repository if its standalone
portfolio or data-generation value justifies the additional maintenance.

## 17. Scope discipline

The Lab must resist unnecessary sophistication.

In particular:

> **The ABM is a vassal of the Lakehouse Lab.**

Its primary purpose is to generate useful, controlled data for the Lab.

Do not add:

-   a more sophisticated agent architecture;
-   a second application;
-   unnecessary orchestration;
-   additional engines;
-   streaming;
-   additional observability platforms;
-   additional frameworks

unless the current Lab objectives provide a concrete reason.

## 18. Working agreement

-   Work with one coding agent/tool at a time.
-   Before switching tools, inspect status, validate the current slice,
    commit a meaningful checkpoint, and push when appropriate.
-   Treat this document and `AGENTS.md` as durable project context.
-   Review OpenTofu plans before destructive cloud operations.
-   Suspend or destroy billable compute after learning sessions.
-   Never commit secrets, raw exports, or identifiable data.
-   Document decisions, trade-offs, limitations and evidence rather than
    presenting assumptions as facts.

Potential future experiments include:

-   Fivetran;

-   Debezium;
